## 1. Executive Summary

This report presents the findings of a comprehensive technical audit of the Numotirus project, a decentralized communication protocol implementation. The audit covered the following modules: Crypto (C++ and C API), P2P Network Layer, DHT Routing Table, NAT Traversal, ZRTP Protocol Implementation, TCT Obfuscation Module, and Transport Layer.

Based on the analysis, the project currently does not meet standards suitable for production deployment. The primary concerns fall into three categories:

1. **Protocol Selection:** The use of ZRTP for key exchange, which has been deprecated by major open-source projects and has known security limitations documented in both academic literature and government disclosures.
2. **Implementation Quality:** The P2P layer contains concurrency issues, resource management errors, and potential memory safety violations.
3. **System Integration:** The C and C++ APIs are not mutually compatible, and several subsystems (ICE, NAT traversal) are incomplete.

The report provides detailed evidence for each finding and recommends corrective actions.

## 4. Detailed Findings

### 4.1. Protocol Selection: ZRTP

**Observation:** The project implements the ZRTP (Zimmermann Real-time Transport Protocol) for key exchange, including SAS generation and trust storage.

**Assessment:**

- **Industry Deprecation:** The primary ZRTP implementation libraries (libzrtpcpp) have been marked deprecated by multiple distributions, including FreeBSD ports, with expiration dates set. The FreeSWITCH project removed ZRTP support citing upstream abandonment.
- **Known Limitations:** Academic analysis has identified vulnerabilities in the SAS verification mechanism under active adversary models. The protocol assumes human out-of-band verification, which may be circumvented through social engineering or AI-assisted impersonation.
- **Alternative Availability:** Mainstream secure communication platforms (Signal, Wire, WebRTC implementations) have moved to DTLS-SRTP, which provides similar functionality with ongoing maintenance and standardization.

**Recommendation:** Replace ZRTP with a protocol that has active maintenance and community support, such as DTLS-SRTP or the Noise Protocol Framework.

---

### 4.2. Crypto Module: API Incompatibility

**Observation:** The project provides both C++ and C interfaces to cryptographic functionality. The key derivation function differs between the two implementations.

**Code Evidence:**

C++ version (crypto.cpp):

```cpp
std::array<uint8_t, KEY_SIZE> derive_key(
    const std::array<uint8_t, SHARED_SECRET_SIZE>& shared_secret,
    const std::string& salt) {
    // BLAKE2b with salt appended
}
// Called as: derive_key(shared, "ecies");
```

C version (crypto_c.c):

```c
static void derive_key(const uint8_t* shared, uint8_t* key) {
    crypto_generichash(key, SYMMETRIC_KEY_SIZE, shared, SHARED_SECRET_SIZE, NULL, 0);
}
```

**Impact:** Ciphertext generated by `encrypt_public` (C++) cannot be decrypted by `decrypt_private` (C), and vice versa. This renders the API unusable for any application that may use both interfaces.

**Recommendation:** Use a single implementation (preferably the C++ version with HKDF-style domain separation) and provide thin C wrappers around it.

### 4.3. Crypto Module: Memory Management

**Observation:** The ephemeral key material is not explicitly zeroed before returning.

**Code Evidence (crypto.cpp):**

```cpp
std::array<uint8_t, SECRET_KEY_SIZE> ephemeral_secret;
std::array<uint8_t, PUBLIC_KEY_SIZE> ephemeral_public;
crypto_box_keypair(ephemeral_public.data(), ephemeral_secret.data());
// ... uses ephemeral_secret ...
// No sodium_memzero call before function exit.
```

**Impact:** Sensitive cryptographic material may remain in memory after the function returns, potentially appearing in core dumps or being read by other processes.

**Recommendation:** Call `sodium_memzero(ephemeral_secret.data(), ephemeral_secret.size())` before returning.

### 4.4. P2P Layer: Thread Synchronization

**Observation:** The `P2PNode` structure contains multiple flags that are accessed from different threads without explicit synchronization.

**Code Evidence (p2p.cpp):**

```cpp
struct P2PNode {
    volatile int running;        // Modified by main thread, checked in receiver
    int peer_ready;              // Set by user, read by sender
    int zrtp_exchanging;         // Modified by both user and callback
};
```

**Technical Analysis:** The `volatile` keyword does not provide atomicity or memory ordering guarantees. Concurrent reads and writes to these variables constitute data races under the C++ memory model, resulting in undefined behavior.

**Recommendation:** Use `std::atomic<int>` for these flags, or protect access with a mutex.

---

### 4.5. P2P Layer: Use-After-Free Risk

**Observation:** The receive callback captures a raw pointer to the `P2PNode` instance.

**Code Evidence (p2p.cpp):**

```cpp
P2PNode* raw = n;
n->transport->SetReceiveCallback(
    [raw](const NodeId& from, const std::string& src_ip, uint16_t src_port,
          const uint8_t* data, size_t len) {
        if (raw && raw->on_message) {
            raw->on_message(src_ip.c_str(), src_port, data, len);
        }
    }
);
```

**Risk:** If the `P2PNode` is destroyed before the `transport` removes the callback, the lambda may be invoked on a freed object. The `raw && raw->on_message` check does not prevent use-after-free; it only checks for null pointer. The pointer becomes invalid immediately after `free(n)` is called.

**Recommendation:** Use `std::weak_ptr` or ensure the callback is removed during destruction before the object is freed.

---

### 4.6. P2P Layer: Resource Management

**Observation:** Several error paths in initialization functions do not fully clean up resources.

**Code Evidence (p2p.cpp):**

```cpp
n->kcp = ikcp_create(KCP_CONV, &n->kcp_ctx);
if (!n->kcp) {
    CLOSE(n->sock);
    free(n);
    return NULL;
}
```

**Issue:** The mutex (`kcp_mutex`) has already been initialized by this point, but it is never destroyed in this error path. This leaks a synchronization object handle on Windows.

**Recommendation:** Use RAII wrappers for all system resources, or ensure every error path performs complete cleanup.

---

### 4.7. P2P Layer: DHT State Duplication

**Observation:** The P2P module creates its own DHT instance and the Transport module creates a separate internal DHT instance.

**Code Path:**

1. `p2p_create` → `dht_create(dht_id)` (C API)
2. `p2p_create` → `std::make_unique<CombinedTransport>(...)` → `DhtTransport` → internal `DhtClient`

**Impact:** Nodes discovered via the transport layer's DHT are not added to the main DHT handle, and vice versa. This results in inconsistent routing tables and ineffective P2P discovery.

**Recommendation:** Use a single DHT instance shared by all components, or design the transport layer to forward discovered nodes to the main routing table.

### 4.8. NAT Traversal Module: Incomplete ICE Implementation

**Observation:** The `TryIce` method contains no functional ICE logic.

**Code Evidence (nat_traversal.cpp):**

```cpp
bool NatTraversal::Impl::TryIce(const Candidate& target) {
#ifdef HAVE_LIBJUICE
    std::cout << "[NAT] ICE to " << target.ip << ":" << target.port << "\n";
    // Placeholder: actual ICE implementation would go here.
    return false;
#else
    std::cout << "[NAT] ICE unavailable (libjuice not compiled)\n";
    return false;
#endif
}
```

**Impact:** Despite the presence of `libjuice_wrapper.cpp/hpp`, ICE is not actually implemented. The `p2p_nat_start_traversal` function also logs results without taking further action to establish connections.

**Recommendation:** Complete the ICE implementation or remove the placeholder code. If ICE is not intended, remove the dependency on libjuice.

### 4.9. DHT Module: Bootstrap Node Management

**Observation:** The list of bootstrap nodes is hardcoded in the source.

**Code Evidence (dht_c.cpp):**

```cpp
std::vector<std::pair<std::string, uint16_t>> bootstrap_nodes = {
    {"dht.transmissionbt.com", 6881},
    {"dht.libtorrent.org", 25401},
    // ... 20+ entries
};
```

**Impact:** If any of these services change their addresses or become unavailable, the DHT cannot bootstrap. There is no mechanism for dynamic updates or DNS-based discovery.

**Recommendation:** Support DNS-based bootstrapping (using SRV records or similar) and allow runtime configuration of bootstrap nodes.

---

### 4.10. TCT Module: Redundant Security Layer

**Observation:** The Tesla Coil Transform provides a reversible transformation layer between plaintext and the AEAD encryption.

**Technical Analysis:** The module's own documentation states: "TCT itself does not provide security. Security is provided by the outer XChaCha20-Poly1305 (AEAD)."

The transformation uses a fixed `secret` and timestamp `now`:

- `r = ln(now + secret)`
- Three-layer EML transform: `exp(x) - ln(w)`

If the AEAD is secure, the transformation adds no security value. If the AEAD is compromised, the transformation does not protect the plaintext because it is deterministic and reversible given knowledge of the secret and timestamp.

**Impact:** Added computational overhead, quantization error, and attack surface without corresponding security benefit.

**Recommendation:** Remove the TCT module and use the AEAD encryption directly.

---

### 4.11. Transport Layer: Synchronous Resolution

**Observation:** The `Resolve` method in `DhtTransport` blocks until a result is found.

**Code Evidence (transport.cpp):**

```cpp
std::optional<std::pair<std::string, uint16_t>> DhtTransport::Resolve(const NodeId& target) {
    auto nodes = impl_->client_->IterativeFindNode(target, 8);
    // ... blocking call
}
```

**Impact:** In a single-threaded or limited-thread environment, this could block the caller for the duration of the DHT lookup (potentially several seconds). This may not be suitable for real-time applications.

**Recommendation:** Consider providing both synchronous and asynchronous (callback-based) resolution methods.

---

### 4.12. ZRTP Implementation: Functional but Protocol-Deprecated

**Observation:** The `zrtp.c` implementation correctly uses libsodium's `crypto_kx` and generates SAS via BLAKE2b. The trust store (file-based) is functional.

**Assessment:** The implementation is technically correct for the ZRTP specification. However, the protocol specification itself is deprecated and has known security limitations (as documented in Section 4.1). The quality of the implementation does not mitigate the protocol-level issues.

**Recommendation:** As per Section 4.1, migrate to a maintained protocol.

## 6. Recommended Actions

### Immediate (Blocking)

1. **Replace ZRTP** with DTLS-SRTP or the Noise Protocol Framework. The current protocol is deprecated and has known vulnerabilities.

2. **Unify the C and C++ encryption APIs** to use the same key derivation scheme. The current inconsistency makes the module unusable for mixed-language applications.

3. **Fix the thread safety issues in the P2P layer** by using `std::atomic` for flags and ensuring proper mutex coverage for all shared state.

4. **Remove the use-after-free risk** in the receive callback by using weak references or ensuring callback lifetime management.

### Short-Term

1. **Complete the ICE implementation** if NAT traversal is a requirement, or remove the placeholder code.

2. **Merge the DHT instances** so that a single routing table is shared across the P2P and transport layers.

3. **Add memory zeroization** for all cryptographic key material.

4. **Remove the TCT module** unless a specific use case is identified that justifies the overhead.

### Long-Term

1. **Define a formal threat model** for the project, specifying the intended adversary capabilities and security guarantees.

2. **Add post-quantum key encapsulation support** through an extensible interface.

3. **Implement comprehensive unit and integration tests** covering threading, error paths, and cryptographic edge cases.

4. **Establish a security audit cycle** for all future releases.

---

## 7. Conclusion

The Numotirus project demonstrates several well-executed components (DHT routing, STUN client, numerical transformation), but these are undermined by fundamental issues at the architectural level. The selection of ZRTP and the inconsistencies in the cryptographic API are the most significant concerns. The P2P layer's concurrency and memory safety issues would likely result in crashes or security vulnerabilities in production use.

Based on the current codebase, the project is not recommended for production deployment. With significant refactoring and the recommended protocol changes, the project could be brought to a usable state. The estimated effort is substantial and would likely require redesigning the P2P and transport layers.
